# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

huckepack is a website that collects and visualises data about official long-distance hiking trails worldwide, focused on well-known thru-hiking routes: one page per trail plus comparisons across trails.

**Mission (docs/mission.md): huckepack helps outdoor enthusiasts find the long-distance trail that suits them, and plan the journey with the data that matters on the way, from official and open sources, named on every page and comparable across trails.** Base every decision on it: before building a feature, adding a trail or data source or changing a design, check it against the mission's checklist ("Deciding on something new"): does it help find a trail or plan the journey, which planning question does it answer, is there an official or open source every figure can name, can it be shown the same way on every trail, does it keep the pages calm, accessible and fast. Say so when a request doesn't fit the mission, and propose what would. docs/scope.md holds decisions and open questions (record new decisions there), docs/data-sources.md lists sources with their licences, docs/roadmap.md ranks candidate trails and features (update it when one is built).

## Commands

```bash
npm install          # once (inside Claude Code's sandbox: npm_config_cache="$TMPDIR/npm-cache" npm install)
npm run dev          # local site at http://localhost:4321; runs detached (npx astro dev status | logs | stop)
                     # before starting: lsof -nP -iTCP:4321 -sTCP:LISTEN; if one is running, reuse it (it reloads
                     # on file changes). Claude Code's sandbox can't stop a detached server; the user has to.
                     # After changing `src/content.config.ts` (delete `.astro/data-store.json` first, or the restarted server reuses stale content) or adding an npm dependency, the server must be restarted: a running server serves
                     # the new package as "504 outdated dependency" and the page breaks.
                     # Dev errors (e.g. a bare "FailedToLoadModuleSSR" page) are logged in .astro/dev.log. Create a new
                     # component file before importing it; if an import failed meanwhile, touch the importing file.
npm run build        # dist/: the static site; fails if a trail file doesn't match the schema
npm run check        # type check (Astro, Svelte, TypeScript)

python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # once (PyYAML, truststore)
.venv/bin/python -m pipeline.routes <slug>             # map line: OSM ways matched to the stages' tracks (cached in data/raw/<slug>/)
.venv/bin/python -m pipeline.routes <slug> --refresh   # download tracks and OSM ways again
.venv/bin/python -m pipeline.water <slug>              # drinking water and springs near the route (after routes)
.venv/bin/python -m pipeline.surface <slug>            # surface categories along the route (after routes)
.venv/bin/python -m pipeline.elevation <slug>          # elevation profile (after routes; Copernicus GLO-30 tiles, downloaded once into git-ignored data/dem/)
.venv/bin/python -m pipeline.access <slug>             # road distance from the record's travel hubs to the start (OSRM)
.venv/bin/python -m pipeline.landcover <slug>          # landscape along the route (after elevation; ESA WorldCover, read remotely)
.venv/bin/python -m pipeline.climate <slug>            # climate by month at the lowest and highest point, daylight (after elevation; ERA5 via Open-Meteo)
```

Inside Claude Code's sandbox, pip needs `PIP_CACHE_DIR="$TMPDIR/pip-cache"`. Python downloads verify certificates through the OS trust store (`truststore`); never disable verification.

## Architecture

- `data/trails/<slug>.yaml`: the trail database, one file per trail; the file name is the URL slug. `src/content.config.ts` is its schema (Zod): every figure names a `source` id from the trail's `sources`, and the build fails on an unknown id. A source's `retrieved: null` means its figures are not yet checked; the page says "not yet verified". `notes` holds discrepancies between sources and open questions; they are for us, not shown on the page.
- `src/lib/trails.ts`: derived figures, never stored: totals from the main stages (`kind: main`; approaches and variants are excluded), averages per day (only when days and stages share a source), and the SAC grade for filtering (stated; converted from CAI with `CAI_TO_SAC`; or, when no grade is published, our estimate in the record's `difficulty.estimated` with a `basis` sentence from the source's description, shown in the popover). Every place that explains the grade says `SAC_NOTE`: grades are translated into the SAC scale to compare trails, but stay an estimate. Each result carries its source.
- `pipeline/`: Python, downloads and processes source data into `data/raw/<trail>/` (committed cache, with `manifest.json` retrieval times; official GPX tracks are copyrighted and git-ignored, so a fresh clone needs `--refresh` once; never commit them, the repo is public) and writes derived data. The site build never downloads. `pipeline/routes.py` builds `public/routes/<slug>.geojson`: one simplified LineString per stage (number, kind, coverage) of OpenStreetMap geometry, matched by `pipeline/osm.py` to the stage's `track` (GPX). The matcher fetches OSM ways within 200 m of the track (Overpass, cached as `osm-stage-*.json`) and takes the cheapest path from start to end, where a way costs its length × (1 + (distance from track / 15 m)²). The GPX only guides the choice; none of its geometry is published. Trails without GPX (Laugavegur) set `route.relation` (the OSM hiking relation) and an `end` point per stage: the relation's main ways (plus `route.alternatives`, ways with role alternative that close gaps) are chained from the start into one line, cut at the stage ends, and each piece guides the matcher like a track (`relation_line`, `split_at`; a jump over `MAX_RELATION_GAP_M` ends the chain and the leftover ways are reported). The printed report flags stages where less than 95% of the track is within 30 m of the result: usually OSM is missing a path there; record it in the trail's `notes`.
- `data/derived/<slug>.json`: data the pipeline derives for a trail, never edited by hand; the `derived` collection in `src/content.config.ts`. `water` (from `pipeline/water.py`): OSM drinking water (amenity=drinking_water/water_point, man_made=water_tap, springs tagged drinking_water=yes) and other springs within 250 m of the route, each with its stage and km along the main route (measured on the map line), counts per stage, and the longest stretches without drinking water / any water. Its `source` must be an id in the trail's `sources` (`osm`). A record can add drinking water a source names that OSM lacks (`waterPoints`, e.g. FÍ's hut taps on the Laugavegur): those points carry their own `source`, OSM drinking water within 100 m of one is the same tap and dropped, the derived `extraSources` lists them, and the chart's (i) and the explanation name them. `access` (from `pipeline/access.py`): for each hub in the record's `access` list (the nearest major hubs only: a main railway station, or where there is no railway the main bus station the trail's buses leave from (`kind: bus`, e.g. Reykjavík BSÍ), and international airports, no small local stations; chosen by hand, coordinates from OSM; no notes), the road distance and driving time to the start from the public OSRM demo server (light use only; source `osrm`) and the straight-line distance.
- Sleeping: records list types (`SLEEPING_TYPES`); pages and the search filter group them into `SLEEPING_CATEGORIES` in `src/lib/trails.ts`, in this order: wild camping (from the record's `wildCamping`, no types), camping, huts, hostels, rooms. Category labels must fit one line in a fifth of the page width (the sleeping strip has five columns), so keep them short. Every type belongs to exactly one category; add new types to a category there. `SLEEPING_LABELS` are generic and in sentence case; local names (rifugi, refugios) belong in a trail's own text.
- Elevation (`pipeline/elevation.py`): samples the main stages every 100 m on the map line (same kilometres as water and surfaces), heights from the Copernicus DEM GLO-30 (30 m grid, source `copdem`): its 1° GeoTIFF tiles come from AWS Open Data (no account) into git-ignored `data/dem/` (30–45 MB each, shared by all trails), read with rasterio and interpolated bilinearly; the sampled heights are cached in `data/raw/<slug>/elevation-glo30.json`. It is a surface model, so in forests it measures the treetops. Its licence requires the notice in the source record ("produced using Copernicus WorldDEM-30 …") and the liability disclaimer in the legal notice; keep both. National lidar models (Saxony DGM1, Czech DMR 5G) are candidates in docs/data-sources.md, not in use: one profile must not mix terrain models. After rerunning this step, rerun pipeline.climate (its places are the highest and lowest point). The page shows it in the Terrain section (below). Its heights come from the terrain model and are not mixed with the stated stage elevations or ascent.
- Surfaces (`pipeline/surface.py`): `pipeline/routes.py` records which OSM ways each stage uses (`routeWays` in the derived file); the surface step downloads their tags and sorts them into natural ground, gravel, paved (surface tag first; ways tagged only `unpaved` or untagged are inferred from the way type: footpaths natural, tracks and roads gravel; the inferred share is reported and shown) or unknown. Runs are placed on the same map-line kilometres as water (each stage scaled to its simplified length), so the charts line up. The page shows them in the Terrain section's ground view (below); colours `--surface-*` in `Base.astro` (also on the search cards and home page), natural colours in a fixed order: natural ground earth brown, gravel sand, paved asphalt grey (issue #15). Checked with the dataviz validator in light and dark mode: separation passes for normal and colour-blind vision; the grey fails the chroma floor by design and differs by lightness (darker than earth and sand in light mode, lighter in dark mode), and every category is named in text, so keep that when changing them.
- Landscape (`pipeline/landcover.py`, issue #3): ESA WorldCover 2021 (10 m land cover, CC BY 4.0, source id `worldcover`) at the elevation profile's samples (`route_samples()` in `pipeline/elevation.py`, shared, so both have the same kilometres; rerun it after the elevation step), read remotely from its COG tiles with rasterio; each sample takes the majority class of its 30 m square so the path itself doesn't read as bare ground. The 11 classes fold into six groups (forest, grassland and shrubs, moss and lichen, bare rock and sand, water snow and ice, farmland and villages; `GROUPS`): more colours don't stay apart for every reader. The derived `landcover` has the shares, runs along the route and the highest sample in forest. The page's Landscape section (after Terrain) shows one lane per group (no lead sentence, removed by request; the sentence built from the shares, "Mostly bare rock and sand (53%), with …", is the chart's accessible name, and the derived `highestForest` is not shown) present along the route with its share and stage ticks (a faceted strip: identity is the row and its label, so the colours `--land-*` only need to differ in their fixed order; checked with the dataviz validator in both modes). The key figure "Landscape" (issue #17) names the main group by its short name (`LAND.short`: Forest, Grassland, Moss, Rock, Water, Farmland; capitalised, "Mostly Rock", "Mainly …" under 50 %) over a small bar of every group's share in the section's colours and order; its popover lists the groups with full names and shares and links to the section. It is satellite land cover, not botany: it says what the landscape looks like, not which plants grow there.
- Steepness: `gradients()` in `src/lib/trails.ts` derives it from the elevation profile at build time (no pipeline step), in walking direction and within each stage only: consecutive stages on the map line can be hundreds of metres apart, and a gradient across that jump is fake. Bars are 200 m, the steepest climb and descent the steepest 500 m, steep means ≥ 15 % (`STEEP_PERCENT`). It colours the Terrain profile (below).
- Terrain (issue #15; of four previews, D was chosen and refined): one section for elevation, steepness and the ground under one elevation profile (the old Surfaces, Elevation and Steepness sections). A two-way toggle (`role="switch"`, a vertical track, in the guidebook margin from 1080 px, above the chart below that) switches between two views: **Elevation** (with the steepness), the profile's 200 m slices filled on a smooth diverging ramp by their gradient (`rampFill()`: the profile's tint `--terrain-tint` at 0 %, `--grade-up-steep` / `--grade-down-steep` at ±30 % (`RAMP_MAX`) and beyond, mixed in OKLab; climbs warm, descents violet; the key is the same ramp as a bar) with height gridlines and the peak, and **Surfaces**, the same slices filled by the surface at their middle. Above the chart, one row of key figures per view (five columns from 640 px, two on phones): highest point, lowest point, steepest climb, steepest descent (the gradient popover has the stage, degrees and metres over 500 m), km steeper than 15 % (popover: up and down); or each surface's share and km. Nothing moves when toggling: both figure rows share one grid cell, as do both keys (the inactive one is only hidden), so keep that when adding to either view. One crosshair tooltip shows height, gradient, stage and ground at the pointer. Its (i) names both sources and the methods; the svg's label summarises both views.
- Climate (`pipeline/climate.py`): 30 years (1995–2024) of daily ERA5 weather from the Open-Meteo historical API at the trail's lowest and highest point (coordinates from the elevation step), adjusted to their elevation, averaged per month (day high, night low, wet days ≥ 1 mm, snow days ≥ 1 cm, frost nights, precipitation, the mean daily top wind and stormy days with gusts ≥ 70 km/h; the wind feeds the difficulty rating, the climate chart doesn't show it yet); daylight is computed for the 15th of each month. Source id `era5`. The page shows season ranges (day highs low down, night lows up high, wet days, daylight) and one chart in three panels over twelve month columns, each panel with its own scale: temperature range bars for both places (`--clim-low`, `--clim-high`), wet days at the high point with snow days as their lower segment (`--wet`, `--snow`), and daylight as a filled share of 24 h (`--daylight`, a strong yellow; in light mode below 3:1 on cream, so every pill keeps its printed value); the two places are named "lowest point" and "highest point" everywhere (strip, legend, tooltip, table), without their heights; the record's season months are shaded. Hover or tap a month for all its figures; a screen-reader table carries the same numbers.
- Difficulty (issue #16, `src/lib/difficulty.ts`, rule and reasons in docs/difficulty.md): three dimensions, Terrain (path grade = the SAC grade, climbing per km, steep stretches, natural ground), Climate (heat, cold, wet days, snow, wind; rated per month, the trail's rating spans its season months, e.g. "Moderate to Hard") and Effort (the longest day), each Easy/Moderate/Demanding/Hard (`LEVELS`). Each measure has three fixed thresholds (`SCALES`, the same for every trail); a dimension takes its hardest measure, never an average, so the page names what set it. The SAC grade is a terrain measure, not its own dimension (it would repeat half of Terrain); the search filter still uses it. The key figure "Difficulty" shows one bar per dimension (its initial beneath, as tall as its level; climate's season range lighter on top) and the hardest level as a word; its popover lists each dimension with what set it and links to the section. The Difficulty section (after the map) is a strip of one card per dimension: the label is an Explain term with each measure's four bands (the trail's band marked), then the level with a four-mark meter (`src/components/Meter.astro`: shape carries the level, not colour) and every measure with its value and month or stage, the one that set the level in bold; Path grade opens the SAC scale popover. It is our own rating from the page's figures; the section shows no source line (removed by request), each measure's popover says where it comes from.
- Water: availability (`WATER_LEVELS`: frequent ≤ 10 km, regular ≤ 20 km, scarce beyond, by the longest stretch without drinking water). The page shows three figures (drinking water points, springs, longest dry stretch with its rating) and a strip chart of the main route: drinking water as filled `--water` dots, springs hollow, stage starts as ticks (`water.stageStarts`), the longest dry stretch as a shaded band; each dot shows a tooltip on hover or tap (a small script in the trail page; one `.tip` element per chart; Esc or a tap elsewhere closes it); stage labels sit centred on each stage's stretch, the 0 km and total km on a line below; the chart has a text summary as its accessible name. Chart kilometres are on the map line and cover the main route only; the counts include approach and variant.
- Icons: `src/components/Icon.astro` inlines Lucide icons (`lucide-static`, ISC) as SVG at build time, decorative unless given a `label`. Used for travel hubs (train/plane, labelled) and home page features only. Key figures, sleeping labels and stage figures carry no icons: words, units and arrows (m ↑, m ↓) say what a number is, and fewer marks keep the page calm. New icons: import the SVG in `Icon.astro` and add it to `ICONS`.
- Key figures, sleeping and water share one design: a strip (`.strip`: a rule in text colour on top, hairlines between items, no filled boxes). The key figures sit in one row from 1200 px (`.key-figs`: each column as wide as its figure, the spare width shared out), in rows of four from 640 px and two columns on phones; ascent and descent share one tile as two small lines (`.climbs`, as tall as one big number, estimates with ≈ before each), so seven figures fit the 1200 px row. Figures are value first, large serif number with a small unit, label small beneath (the Season key figure shows the search cards' month cells in two rows of six instead of a number, as tall as the numbers beside it, with the record's wording for screen readers) (`dt` before `dd` in the markup, reordered by CSS). Status is a shape plus a word (`STATUS` in the trail page: full = available/allowed/frequent, half = restricted/regular, crossed = prohibited/scarce, empty = none listed); the colour tokens `--good/--fair/--poor` only fill the shape, text stays in text colours. The wild camping rule follows the sleeping strip, led by the same mark. Location is one grid of label-over-value items (`.loc`, 4 columns on desktop, 2 on phones; `.wide` items span 2), so rows always align whatever the content; it reads start, finish, travel hubs, country, regions, protected areas, waymarking, route type, managed by (waymarking shows the trail's mark redrawn small before its text when a source describes it: the record's `waymarking.symbol`, drawn by `src/components/Waymark.astro` in the paint's own colours, decorative; today the CAI red-white-red flag and the Forststeig's yellow vertical stripe on bark; marks no source shows, like the Laugavegur's stakes, get none, and official logos are not copied) (route type sits there, not in the key figures, and fills the last row). Long values get `.wide`. Stages are a timeline with figures in aligned columns, one line per stage from 820 px, under a quiet text header (Distance, Ascent, Descent, Elevation, Time; column widths in rem so header and figures line up; Elevation and Time only when some stage has them, with an empty cell for a stage that lacks one). Stage ascent and descent are optional in the record (some sources give neither); `stageTotals()` sums them only when every main stage has them. A stage time can be a range (`minutes` to `maxMinutes`, shown "4–5 h"). Where the source gives no stage heights, climbs or times, `stageEstimates()` in `src/lib/trails.ts` fills them: heights from the elevation profile at each main stage's first and last sample, ascent and descent as the sum of the climbs and drops between its 100 m samples (all to 10 m; the key figures then show the summed estimate with ≈), times by DIN 33466 (`walkingMinutes()`) from the stage's own stated distance, ascent and descent, so a time never mixes sources. Estimates are muted and marked ≈ (screen readers hear "estimated"), the note under the table names the methods, and published figures are never replaced; narrower screens drop the header and rely on units and arrows. The map shows only the route and termini. Keep the page compact: sections 36 px apart, map 11:5 on desktop. From 1080 px, section headings sit in a left margin column (136 px, floated) and each section's content is indented 160 px beside its title, like a printed guidebook: it separates sections without rules or bands and saves the heading rows. Narrower screens stack as before; the 1080 px breakpoint keeps the content column at least 820 px wide (one-line stage timeline, five sleeping columns). Key figures and map (hidden headings) keep the full width. Phones (below 640 px): every chart svg sits in a `.chart-scroll` strip that scrolls sideways at a readable 800 px (labels 13 px), while legends and captions stay put; `.spec.three` strips put the third figure on its own row (steepness: one per row); sleeping shows wild camping across the top and the four bed categories in two columns. Touch screens (`pointer: coarse`) get taller filter chips and segmented buttons and 26 px slider thumbs. No page may scroll sideways: screen-reader tables go inside a `div.sr-only` (a table ignores the 1 px width of `.sr-only`), and `.spec.cols` strips keep two columns on phones. Colours in `Base.astro` (including `--water`) were checked for WCAG AA in both modes; check new ones too.
- Explanations: `src/components/Explain.astro` makes a label itself the button (`term`, dotted underline, no "?" icon) that opens a popover (`popover` attribute, no JavaScript; closes with Esc, a click outside or Close); the slot holds the text. With `shared`, it renders only the term and opens another Explain's popover of that id (two labels, one text: the steepest climb and descent share "Gradient", which explains %, metres and degrees with a reference table). Used for the difficulty key figure and each difficulty dimension, the SAC scale on the Path grade measure (`SAC_SCALE`), the terrain figures and for every sleeping and water card (sleeping texts are the `hint` of each `SLEEPING_CATEGORIES` entry). Strips show no hint lines; explanations live in the popovers. `src/components/Explain.svelte` is the same for Svelte islands (the search filters); keep the two in step. Charts carry no caption lines: their sources and methods sit behind an (i) (working rule 3); no "hover or tap" instructions (the dotted terms and cursors make interaction discoverable).
- Trail page: sections follow a researcher's questions: where is it (Location, Map), is it for me and when (Difficulty, Climate), what are the days like (Stages, Terrain, Landscape), what do I need on the way (Sleeping, Water); the sources close the page as a footnote. Keep new sections in that logic. An on-page navigation (sticky, on a `--surface` band, links in text colour) links to the sections the trail has; a small script underlines the section in view in the accent colour (`aria-current="location"`) and keeps it visible in the phone row. The page shows no footnote markers: figures are not linked to their source on the page; the sources close the page as a footnote (issue #18: a `footer`, not a section, so it is not in the on-page navigation and not in the guidebook margin layout; 72 px below the last section, a short 120 px rule like a printed footnote's, a small uppercase heading, 0.75 rem muted text) listing every source of the record with its licence (retrieval dates stay in the record, not on the page; an unchecked source shows "not yet verified"). The record still names a source for every figure.
- Maps: `src/components/TrailMap.svelte` (MapLibre GL, `client:visible`) draws the route over an OpenFreeMap basemap (OpenStreetMap data, no API key) that follows the site theme: "liberty" in light mode, "dark" in dark mode, switched live when the theme changes (`setStyle` drops custom layers, so everything is added again on `style.load`; route and termini colours come from the theme tokens). On top: hill shading and contour lines (labelled on major lines from z12; spacing per zoom in `CONTOURS`) from AWS Terrain Tiles (Terrarium PNGs on s3.amazonaws.com, no key), decoded by `maplibre-contour` in its own worker; terrain sits under water, roads, buildings and labels; main stages solid, approaches and variants dashed, start and end as dots. The trail page passes the route only if `route` is set and the file exists; otherwise the map shows just the termini. The attribution names the route's source.
- `route.publishable: false` means the geometry's licence doesn't allow republishing it (official GPX tracks usually don't). Such routes are fine for local work but must not be deployed: replace them with OSM-derived geometry first. `data/raw/` may hold such files too; never copy them into `public/` other than through the pipeline.
- Logo: the 8 × 8 pixel cairn (each stone carried huckepack by the one below). `design/logos/make.py` holds all proposals and writes the chosen one (`FINAL`) to `src/assets/logo.svg` (currentColor; the header shows it at 24 px in the accent colour, a whole multiple of 8 so the pixels stay crisp) and `public/favicon.svg` (plain colours), plus PNGs at whole-number scales of the grid (`apple-touch-icon.png` 180 px on cream, `favicon-32.png` transparent fallback, `icon-512.png` on cream), written with the standard library. Edit the grid there and rerun it; don't edit the outputs.
- Theme: `src/components/ThemeToggle.astro` in the header switches auto (system setting, default) / light / dark, stored in localStorage `theme` and applied as `<html data-theme>`; an inline script in `Base.astro`'s head applies a saved choice before the first paint. Dark tokens live under `:root[data-theme="dark"]` and, for auto, under `prefers-color-scheme: dark` with `:root:not([data-theme="light"])`. Components must use the tokens, not their own `prefers-color-scheme` queries, or they ignore the switch.
- Breadcrumbs: every page except the home page starts with `src/components/Breadcrumbs.astro` (Start › … › current page), right before its `h1`; new page types must add it too.
- Pages: `src/pages/index.astro` is the home page: a centred hero (eyebrow "Long-distance trails, in data", headline "Find your trail. Plan the journey.", three USPs from the mission as a check-marked list (find, plan, sources) instead of a lede paragraph, the main call to action "Explore the trails" to `/trails/` and beside it the outlined secondary "Help me choose" to `/trails/guide/`), a strip of totals in one row from 1080 px (trails, countries, kilometres, official stages, then for fun: metres climbed with the Everest multiple, hours of walking, drinking water points; each summed from the figures the trail pages show: stated climbs and times, else the terrain model's estimate and DIN 33466; they count up from 0 once the strip is first on screen, 1.2 s ease-out, from an inline script right after it so the final numbers never flash first; screen readers get only the final value; nothing moves with reduced motion or without JavaScript), a featured trail (a random one on each page load: every trail's card is rendered, the first visible, and an inline script right after them shows a random one before the first paint; without JavaScript the first stays; countries only, no regions, like the search cards; length, ascent (the terrain model's estimate with ≈ where no stages state it), days, the difficulty as one word (the hardest of the three ratings over the season, as on the trail page) and the highest point, with a mini elevation profile and surface bar and no caption line), what every trail page offers (in the trail page's section order), the data sources, and all trails as cards (length, days, difficulty word). The home page builds the same search record as the search page (`searchSummary()`). `src/pages/trails/index.astro` is the search page (centred h1 and lede): `summarize()` in `src/lib/trails.ts` builds a compact record per trail (with the trail's derived data: season, water rating, surface shares, a coarse elevation profile, for `src/components/TrailList.svelte` (`client:load`), which filters and sorts in the browser (no text search). Filters sit in a sidebar (a full-screen panel behind a "Filters" button below 900 px), grouped by planning question in the order a hiker decides: months (pills; season includes any), continents and countries (several at once, any of them; `toggleWhere()` keeps a continent and its own countries from being chosen together: a continent covers its countries, which show as included, and picking one of them narrows the choice to it; `where=Germany,Italy`), walking days (a two-thumb slider; the trail's days range must overlap), how hard at most (one group, four sliders: the difficulty ratings Terrain, Climate and Effort, Easy to Hard, and the path grade SAC T1–T6; each last stop "Any"; once one is set, trails without that rating drop out; Climate is the hardest of the months picked above within the trail's season, else of its whole season, `climateLevel()`), landscape (pills, any of them; a trail has a landscape when at least 20 % of its main route is that WorldCover group, `LANDSCAPE_SHARE`), share of natural ground (slider), sleeping categories (pills; all of them), wild camping (its own group, segmented), longest stretch without drinking water (slider in km). The search record is `searchSummary()` in `src/lib/search.ts`: `summarize()` plus the difficulty levels, the climate level per month and the landscape shares (kept out of trails.ts, which difficulty.ts imports); the guide uses it too. "Easiest first" sorts by the hardest of the three ratings, then the SAC grade. Sliders are `src/components/Range.svelte` (native range inputs over fixed stops; two stacked for a range; no fill while a slider filters nothing), each with its setting in words beside the group title. Ordered scales get sliders; unordered choices keep pills. "Clear all" is always in the layout, only hidden, so it doesn't shift the filters; the sidebar's focus rings stay inside the column. The sidebar scrolls with the page (no sticky inner scroll box: its scrollbar came and went and shifted the filters), and the filters show no hint lines: each group's label is an Explain term with the details (SAC scale, sleeping categories, water levels, surface key) in its popover. Every filter is a URL parameter (shareable) and shows as a removable chip above the results. No single click leads from some results to none: a pill or segmented button that would leave no trail with the other filters is dimmed and disabled (with a tooltip; one that is on never is, so it can be undone), and a slider marks the stops that would leave none as a dashed track (`live`/`liveLo` in `Range.svelte`) and its thumb won't move onto them. Result cards show the countries (no regions), figures, water and wild camping status (shape plus word), sleeping, a season strip, and the elevation profile on one height scale for all trails (`eleRange`, so profiles compare honestly) with a surface share bar. The filter logic (slider stops, the `Filters` state, `matches()`, URL parameters `toParams`/`fromParams`, the where-choices) lives in `src/lib/filters.ts`, shared by the search page and the guide, so both always agree. `src/pages/trails/guide/index.astro` ("Help me choose") runs `src/components/TrailGuide.svelte`: the same filters as eleven questions, one per screen, in the search page's order (when, where, days, terrain, longest day, weather, landscape, ground underfoot, sleeping, wild camping, water; the difficulty questions answer with our ratings, Easy up to Hard or "anything", so the SAC grade is left to the search page), each answer showing how many trails it would leave (answers that would leave none are disabled, except the current one, so it can be undone; a month is disabled when no trail is in season then); Next reads Skip until something is chosen; each question is a history entry, so the browser's back button steps back; the guide fills the screen below its title and pins Back, the running count and Next in a bar at the bottom (sticky when a phone's answers run longer), so the button stays in one place on every question, and every question fits 1280 × 720 (the progress bar and its counter "3 of 11" share one row, the bar filling n/11 on question n; the intro shows on question 1 only; days, the three difficulty questions, landscape and sleeping take two columns from 900 px); there is no summary: the last question's button ("Show 5 trails", the running count) opens `/trails/?…` with those filters, where the search page's empty state and disabled options take over if nothing matches. Day answers are ranges on the shared stops (1–3, 4–7, 8–14, 15+; 8 and 15 are stops for that). `src/pages/trails/[slug].astro`: one prerendered page per trail. Legal pages: `src/pages/legal-notice.astro` (Impressum, § 5 DDG) and `src/pages/privacy.astro` (GDPR), both on `src/layouts/Legal.astro`, linked in the footer; the operator's personal details (name, street, postcode and city, email) never go into the repository, which is public: `src/lib/operator.ts` reads them at build time from `LEGAL_NAME`, `LEGAL_STREET`, `LEGAL_CITY`, `LEGAL_EMAIL` (the deploy workflow from the repository's Actions secrets, a local build from the git-ignored `.env`), `src/components/Operator.astro` renders the address, and a missing value shows as a `<mark class="todo">` placeholder. `src/components/Email.astro` keeps the email address out of the HTML text (reversed and base64-encoded, made a mailto link by a script; "name (at) example (dot) org" without JavaScript). Both pages ask search engines not to index, cache or quote them (`<meta name="robots" content="noindex, …">` via Base's `personal`) and reserve text and data mining (`tdm-reservation`, against AI training); `public/robots.txt` keeps known AI crawlers off them but doesn't block search engines there (they must fetch a page to see its noindex); the footer links to them are `rel="nofollow"`. The privacy policy lists every third party the site loads (today GitHub Pages, OpenFreeMap and AWS (elevation tiles); fonts and scripts are self-hosted): update it whenever the site starts loading something new (fonts, analytics, ads, embeds). `src/layouts/Base.astro`: header (logo and theme switch only, no navigation links), footer, the page container (`.wrap`: 1200 px of content plus 16 px gutters, centred; the desktop standard for 1280–1440 px screens) and the design tokens (warm palette, serif headings) with dark mode overrides; text colours were checked for WCAG AA contrast in both modes, so check new ones too.

## Ground rules

- Only official trails: a route designated or maintained by a government body or a recognised trail association. Unofficial routes (for example the Hayduke Trail) are out of scope unless docs/scope.md says otherwise.
- Every figure on a page must come from a source listed in the trail's record (or, for sources used across trails, in docs/data-sources.md), with its licence and retrieval date. Check a source's licence before using it: official GPX tracks are often copyrighted, and OpenStreetMap data requires ODbL attribution.
- Trail lengths, elevation gain and similar numbers differ between sources. Show which source a number comes from rather than silently picking one, and never mix them in one figure.

## Working rules

Three rules for all future development (set 2026-10-29), on top of the mission and the ground rules:

1. **Bigger design changes start as a preview with three approaches.** A bigger design change is a new section or chart, a reworked page layout or navigation, a new page type, or a redesign of an existing component (not text edits, bug fixes, small spacing tweaks, or contrast and accessibility fixes). Build three clearly different approaches first, on real data, on one local preview page under `src/pages/preview/<topic>.astro` (labelled "Approach A/B/C", each with a one-line description of its idea and trade-off; check them in both themes and at phone width), on a local branch `preview/<topic>`, and give the user the local URL. Preview pages and branches are never pushed to `main` (everything on `main` goes live). Once the user picks one, build only that into the site on `main` and delete the preview page and branch. Issue #3 (Landscape) was the model for this.
2. **Every new trail's data is double-checked before it is reported done.** Preferred: confirm each figure (length, ascent and descent, days, season, stage distances, times and heights, termini, difficulty, sleeping and camping rules) against a second, independent source (e.g. the tourism board, a national park, a national trail portal, a guidebook publisher's facts). Figures may differ by at most 10 %; a larger difference is recorded in the trail's `notes` and `dataCheck` with both values and named to the user; the page keeps the official figure (docs/scope.md). Derived figures that have an official counterpart (map-line length vs. stated length, highest point vs. stated) are checked the same way. Where no second source exists: build the site and check the figures as the trail page shows them, one by one, against the original source (catches typos and wrong conversions in the record). Either way, add a note to the record ("Data check (date): …" with what was compared and what agrees) and fill its `dataCheck` field: `date`, `against` (the second sources), `pageAgainst` (sources the built page was checked against where no second source exists) and every `deviations` entry over 10 % (`figure`, `ours`, `theirs`, `source`). The check is internal quality assurance: nothing of it is shown on the page, and a source used only for the check gets `checkOnly: true`, so the page's Sources list leaves it out. Give the user the comparison as a table. When a second source publishes a figure the first lacks (e.g. stage times), use it with its own source rather than our estimate (`stages.timesSource`, named under the stage table). All three trails were checked on 2026-10-29.
3. **What explains a chart sits behind an (i).** Sources, methods and reading notes for a graph are not caption lines under it: they go into a popover behind a small (i) icon in the chart's top-right corner (at the end of the legend row where the chart has one on top, else in a slim row of its own above the drawing; `<figcaption class="chart-info">`, absolutely placed with `<Explain icon term="About this chart" title="…">`; `Explain.svelte` has the same `icon` prop), to keep the page calm. The chart itself keeps what is needed to read it at a glance: its legend or key, axis labels and its accessible name. Labels that explain a figure stay dotted Explain terms.
