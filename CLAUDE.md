# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

huckepack is a website that collects and visualises data about official long-distance hiking trails worldwide, focused on well-known thru-hiking routes: one page per trail plus comparisons across trails.

**Mission (docs/mission.md): huckepack helps outdoor enthusiasts find the long-distance trail that suits them, and plan the journey with the data that matters on the way, from official and open sources, named on every page and comparable across trails.** Base every decision on it: before building a feature, adding a trail or data source or changing a design, check it against the mission's checklist ("Deciding on something new"): does it help find a trail or plan the journey, which planning question does it answer, is there an official or open source every figure can name, can it be shown the same way on every trail, does it keep the pages calm, accessible and fast. Say so when a request doesn't fit the mission, and propose what would. docs/scope.md holds decisions and open questions (record new decisions there), docs/data-sources.md lists sources with their licences, docs/roadmap.md ranks candidate trails and features (update it when one is built).

## Commands

```bash
npm install          # once (inside Claude Code's sandbox: npm_config_cache="$TMPDIR/npm-cache" npm install)
                     # Node 22, at least 22.23.4 (Astro 7.4 refuses older): `nvm install 22 && nvm alias default 22`;
                     # inside the sandbox, without that Node: npx -y -p node@22 node node_modules/astro/bin/astro.mjs build
npm run dev          # local site at http://localhost:4321; runs detached (npx astro dev status | logs | stop)
                     # before starting: lsof -nP -iTCP:4321 -sTCP:LISTEN; if one is running, reuse it (it reloads
                     # on file changes). Claude Code's sandbox can't stop a detached server; the user has to.
                     # After changing `src/content.config.ts` (delete `.astro/data-store.json` first, or the restarted server reuses stale content) or adding an npm dependency, the server must be restarted: a running server serves
                     # the new package as "504 outdated dependency" and the page breaks.
                     # Dev errors (e.g. a bare "FailedToLoadModuleSSR" page) are logged in .astro/dev.log. Create a new
                     # component file before importing it; if an import failed meanwhile, touch the importing file.
npm run build        # dist/: the static site; fails if a trail file doesn't match the schema
npm run check        # type check (Astro, Svelte, TypeScript)
npm test             # tests of the figures the site derives (tests/trails.test.ts, Node's test runner)
.venv/bin/python -m unittest discover -s tests   # tests of the pipeline's pure parts (tests/test_pipeline.py)

python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # once (PyYAML, truststore, rasterio, osmium)
.venv/bin/python -m pipeline.new_trail <slug> "<Name>"  # a new record: every field null with what belongs there; the build fails until all are filled
.venv/bin/python -m pipeline.readers.outdooractive <stage page url> …   # stage lines for the record from Outdooractive tour pages (--overview <page>: the stage links on it)
.venv/bin/python -m pipeline.all <slug>                # every step below in order, then a check of the results (start here)
.venv/bin/python -m pipeline.all <slug> --from water   # resume at a step after a failure; --check: only the check; --refresh: download all again
.venv/bin/python -m pipeline.routes <slug>             # map line: OSM ways matched to the stages' tracks (cached in data/raw/<slug>/)
.venv/bin/python -m pipeline.routes <slug> --refresh   # download tracks and OSM ways again
.venv/bin/python -m pipeline.water <slug>              # drinking water and springs near the route (after routes)
.venv/bin/python -m pipeline.surface <slug>            # surface categories along the route (after routes)
.venv/bin/python -m pipeline.elevation <slug>          # elevation profile (after routes; Copernicus GLO-30 tiles, downloaded once into git-ignored data/dem/)
.venv/bin/python -m pipeline.access <slug>             # road distance from the record's travel hubs to the start (OSRM)
.venv/bin/python -m pipeline.landcover <slug>          # landscape along the route (after elevation; ESA WorldCover, read remotely)
.venv/bin/python -m pipeline.climate <slug>            # climate by month at the lowest and highest point, daylight (after elevation; ERA5 via Open-Meteo)
.venv/bin/python -m pipeline.climate --pending         # every trail whose climate is due (after the weather API's daily quota ran out)
```

Keep the large extracts outside the synced project folder with `HUCKEPACK_OSM_EXTRACTS=/a/local/folder` (default `data/osm/extracts/`, git-ignored); the small per-trail corridors stay in `data/osm/corridors/`. OSM data come from Geofabrik extracts read locally (default), or from the public Overpass API with `OSM_SOURCE=overpass` (`OVERPASS_URL` picks a mirror). Hosts a full run needs in the sandbox: download.geofabrik.de, copernicus-dem-30m.s3.eu-central-1.amazonaws.com, esa-worldcover.s3.eu-central-1.amazonaws.com, archive-api.open-meteo.com, router.project-osrm.org, plus the track's host.

Inside Claude Code's sandbox, pip needs `PIP_CACHE_DIR="$TMPDIR/pip-cache"`. Python downloads verify certificates through the OS trust store (`truststore`); never disable verification.

## Architecture

- `data/trails/<slug>.yaml`: the trail database, one file per trail; the file name is the URL slug. `src/content.config.ts` is its schema (Zod): every figure names a `source` id from the trail's `sources`, and the build fails on an unknown id. A source's `retrieved: null` means its figures are not yet checked; the page says "not yet verified". `notes` holds discrepancies between sources and open questions; they are for us, not shown on the page.
- `src/lib/trails.ts`: derived figures, never stored: totals from the main stages (`kind: main`; approaches and variants are excluded; they feed the stages table, per-day averages and difficulty), the trail's length (`trailLength()`: the first stated total in the record, else the stage sum; the key figure, title and search and home-page cards show it, since stage lists often include the paths into the stage towns, e.g. the Moselsteig's 392.8 against 365 km; docs/scope.md), the measured length (`measuredLength()`: the main route's length on the full matched OSM line, the derived `measured` from pipeline/routes.py, used only where every main stage is at least 95 % matched, `MEASURED_MIN_COVER`; the Length key figure's popover names both) the total ascent and descent (`trailClimb()`, the same rule as the length: the stated pair, `ascent` and `descent` from one source, else the main stages' sums when every stage states both, else the page sums the terrain model's estimates, ≈; key figure, search cards and the home page's metres climbed; the key figure's popover names the source and, where they differ, the stage sums; no measured ascent: the surface model reads treetops, 15–60 % high in forest, so it isn't fair to compare by) and the comparable length (`compareLength()`: measured, else the trail's length; search sorting, climbing per km and the home page's total kilometres use it, so lengths compare by one method), averages per day (only when days and stages share a source), and the SAC grade for filtering (stated; converted from CAI with `CAI_TO_SAC`; or, when no grade is published, our estimate in the record's `difficulty.estimated` with a `basis` sentence from the source's description, shown in the popover). Every place that explains the grade says `SAC_NOTE`: grades are translated into the SAC scale to compare trails, but stay an estimate. Each result carries its source.
- `pipeline/`: Python, downloads and processes source data into `data/raw/<trail>/` (committed cache, with `manifest.json` retrieval times; official GPX tracks are copyrighted and git-ignored, so a fresh clone needs `--refresh` once; never commit them, the repo is public) and writes derived data. The site build never downloads. `pipeline/routes.py` builds `public/routes/<slug>.geojson`: one simplified LineString per stage (number, kind, coverage) of OpenStreetMap geometry, matched by `pipeline/osm.py` to the stage's `track` (GPX). The matcher fetches OSM ways within 200 m of the track (from `osm.source()`, see OSM data below; Overpass is queried as padded boxes over 1 km pieces of the track, `osm.boxes()`, since the polyline `around` can silently match nothing; an answer without ways is an error, never cached; cached as `osm-stage-*.json`) and takes the cheapest path from start to end, where a way costs its length × (1 + (distance from track / 15 m)²). Where the track turns back on itself (out to a summit or viewpoint and back the same way: the points 150 m before and after lie together, `turnarounds()`), each leg is matched on its own and the legs chained, since the cheapest path would skip the spur (the Hexen-Stieg's Brocken, the Alpe-Adria-Trail's stages 7 and 30); the same for a short loop out to a viewpoint and back on a parallel path (the track returns within 100 m of where it left after 0.6–3 km, `LOOP_GAP_M`; split at the loop's farthest point; the Moselsteig's stage 3, the Forststeig's stage 5). A split needs an OSM node within 30 m of the turn, so a stray track point can't force a detour. Where the ways near the track don't connect at all (the Sauerland-Waldroute's stage 17 crosses the Ruhr at Bestwig where OSM maps the driveway as removed), the matcher bridges the shortest gap near the track, up to 100 m (`MAX_BRIDGE_M`; way id 0 in `routeWays`, unknown surface), prints it, and the gap goes in the trail's notes; trails whose ways connect are untouched. The GPX only guides the choice; none of its geometry is published. Trails without GPX (Laugavegur) set `route.relation` (the OSM hiking relation) and an `end` point per stage: the relation's main ways (plus `route.alternatives`, ways with role alternative that close gaps) are chained from the start into one line, cut at the stage ends, and each piece guides the matcher like a track (`relation_line`, `split_at`; a jump over `MAX_RELATION_GAP_M` ends the chain and the leftover ways are reported). Where OSM maps a trail as one relation per section (a superroute, e.g. the West Highland Way), each stage names its own `relation` instead (child relations included): chained from where the previous main stage ended, it guides that stage (cached as `osm-relation-<id>.json`). A stage's `relation` can also be a list (an OSM section and the start of the next, e.g. the Westweg's stage 9: section 9 and the western variant's relation), and with an `end` point the stage is cut out of its relations: they are chained from the end nearest the trail's start, and the piece from where the stage begins to the point nearest its `end` guides it (`piece()`; chaining from a point mid-relation could head the wrong way). A variant listed right after another variant chains from that one's end, so a run of variant stages (the Westweg's eastern 9–13, listed after main stage 8 where they branch off) follows on. A `track` can also be a tour page that carries its track as schema.org data (`"geo"` GeoShape `"line"`, as Outdooractive's pages do, e.g. the Alpe-Adria-Trail's touren.kaernten.at stage pages, whose GPX download needs a login); `track_points()` reads either (also the line as "lon,lat,height" triples, eifelsteig.de, and an `@type` list ["GeoCoordinates", "GeoShape"] with the start's coordinates before the line, hermannshoehen.teutoburgerwald.de, and the neusta tour pages' HTML-escaped `"polyline": "lon,lat lon,lat …"`, sauerland-waldroute.de, whose GPX download needs a licence key), and the cached copy keeps the `.gpx` name so it stays git-ignored. Where a stage cut out of its relations by `end` chains clearly less (over 1 km) from the end nearest the trail's start than from the relation's open end (a way end no other way continues from), the open end is used: on the Rothaarsteig's stages 6–8 a way in the middle lay nearer Brilon and the chain stopped after a few ways (`line_km`, `relation_line(..., from_open_end=True)`; the Westweg and the West Highland Way come out identical). The OSM ways per stage are cached by stage (`osm-stage-<n>-<kind>.json`), not by track: delete a stage's cache when its guide line changes. Stage numbers can carry a route letter (the Goldsteig's N8–N23 and S8–S22); the pipeline orders main stages by their digits (`osm.stage_order`). A stage that can't be walked in full (the Eifelsteig's stage 14 since a Kyll bridge was lost in the 2021 flood) gets `closed`: `at` (where it can be walked to), `since`, `reason`, `source` and the operator's recommended `detour`, leg by leg (`by: foot` with `via` points that keep the guide on the recommended path, matched to OSM like a track; `by: train` or `bus` with the OSM `relation` of the line, followed by the shortest way through its ways, `relation_path()`, since a railway's double tracks and junctions defeat chaining). The stage's track is cut at `at` and its coverage counts against the whole track, so the check flags the missing part (note it); the record keeps the stated figures. The legs are features of their own (kind `detour`, `by`), left out of the measured length, water and surfaces; the map draws the walk dotted in the trail's colour and a ride as a thin ink line with ties (a railway on a printed map), each in the legend only when present, and the note under the stage table says what is closed and the recommended way on. Downloads retry on dropped connections; `osm.fetch()` treats an Overpass `remark` with a runtime error (a timeout answered with status 200 and no elements) as a failure and retries instead of caching an empty result, and `pipeline/water.py` queries the bounding box of each piece of about 10 km of the route (`CHUNK`) and filters to 250 m itself: Overpass's polyline `around` sometimes silently matched nothing (on 2026-10-29 it did for every route), and `osm.around()` drops repeated points, which can trip it too. The printed report flags stages where less than 95% of the track is within 30 m of the result: usually OSM is missing a path there; record it in the trail's `notes`.
- OSM data (for scaling to more trails, 2026-10-30): the steps ask `osm.source()` (pipeline/osm.py) four questions, ways near a track, a relation with its ways' geometry, water points in a box, the tags of given ways, and get Overpass-shaped JSON back, so their caches look the same whoever answered. By default `pipeline/osmlocal.py` answers from Geofabrik extracts: for each of the trail's points (GPX tracks, termini, stage ends) the smallest Geofabrik region holding it (`regions_for()`, from Geofabrik's index with region polygons), downloaded once into git-ignored `data/osm/extracts/` (re-downloaded with --refresh when older than 7 days; the dated file name is the extract's date); one pass over each extract (pyosmium, pinned) collects the corridor within 600 m of the points, highway ways with nodes and tags, the named route relations (with children) and their ways, water nodes, cached as git-ignored `data/osm/corridors/<slug>.json.gz` and rebuilt when it doesn't cover the guide points or lacks a named relation. Relation-only trails first collect just the relations' own ways (one pass), whose geometry then defines the corridor for a second pass (a box around a long trail's ends would hold far too much). The extracts come from the termini and stage `end` points only, so a relation-only trail spanning several regions needs a stage `end` in each (the Goldsteig's stage 7 end brings in the Oberpfalz); where relation member ways are still missing after the first pass (a route over a border), the regions around the found ways' ends are read too. The data carry the extract's date, which the caches record as retrieved. Checked against the Overpass results on the Laugavegur and Merano (2026-10-30): identical map lines, route ways and water; Merano's surface tags were stale in the Overpass cache (the step had kept tags from before stage 4 changed) and are now complete. `pipeline/all.py` runs every step in order (routes, water, surface, elevation, landcover, climate, access), drops the caches that depend on the map line when routes changed it (the stale-tags trap; not the climate downloads, which the climate step checks against the grid cells itself), stops at a failing step with the command to resume (except the climate step: when Open-Meteo's daily quota is used up, about 10,000 calls a day with one place of 30 years counting as about 780, so about six trails a day, it leaves the trail pending, `pending()`, and the run goes on; `pipeline.climate --pending` catches up later, and the check flags it: don't publish a trail before its climate is in), and ends with `check()`: stages under 95 % matched, stage and route lengths more than 10 % off the map line, stated against terrain-model ascent, a dry stretch over 25 km, over 10 % unknown surface, hubs over 300 km away, no `dataCheck`, and a route above 1,500 m without `treeLine` or a "Tree line" note.
- Adding trails: the "Add a trail" issue form (`.github/ISSUE_TEMPLATE/add-trail.yml`) collects what a record needs (official name, managing body, stage list, track or OSM relation, season, sleeping and camping, a second source); `pipeline/new_trail.py` writes the record skeleton; `pipeline/readers/outdooractive.py` reads stage figures and the stage page as `track` from three portal layouts: Outdooractive (English or German labels; titles "Stage 7 …: A - B" or "7. Etappe - von A nach B"; e.g. touren.kaernten.at, touren.harzinfo.de, whose collection pages list a trail's stages), toubiz ("Distanz", e.g. schwarzwald-tourismus.info; no track) and destination.one (figures in `title` attributes, e.g. baiersbronn.de, with the page's own GPX download as the track); tested on all 44 Alpe-Adria-Trail pages (identical to the record); `pipeline.all` builds and checks. Regional facts reused across trails live in `data/reference/` (today `tree-lines.yaml`: each region's tree line with its source's words, its second source and the trails using it); a record still copies the figure and source into its own fields, since every figure names its source on the trail page.
- `data/derived/<slug>.json`: data the pipeline derives for a trail, never edited by hand; the `derived` collection in `src/content.config.ts`. `water` (from `pipeline/water.py`): OSM drinking water (amenity=drinking_water/water_point, man_made=water_tap, springs tagged drinking_water=yes) and other springs within 250 m of the route, each with its stage and km along the main route (measured on the map line), counts per stage, and the longest stretches without drinking water / any water. Its `source` must be an id in the trail's `sources` (`osm`). A record can add drinking water a source names that OSM lacks (`waterPoints`, e.g. FÍ's hut taps on the Laugavegur): those points carry their own `source`, OSM drinking water within 100 m of one is the same tap and dropped, the derived `extraSources` lists them, and the chart's (i) and the explanation name them. `access` (from `pipeline/access.py`): for each hub in the record's `access` list (the nearest major hubs only: a main railway station, or where there is no railway the main bus station the trail's buses leave from (`kind: bus`, e.g. Reykjavík BSÍ), and international airports, no small local stations; chosen by hand, coordinates from OSM; no notes), the road distance and driving time to the start from the public OSRM demo server (light use only; source `osrm`) and the straight-line distance.
- Sleeping: records list types (`SLEEPING_TYPES`); pages and the search filter group them into `SLEEPING_CATEGORIES` in `src/lib/trails.ts`, in this order: wild camping (from the record's `wildCamping`, no types), camping, huts, hostels, rooms. Category labels must fit one line in a fifth of the page width (the sleeping strip has five columns), so keep them short. Every type belongs to exactly one category; add new types to a category there. `SLEEPING_LABELS` are generic and in sentence case; local names (rifugi, refugios) belong in a trail's own text.
- Elevation (`pipeline/elevation.py`): samples the main stages every 100 m on the map line (same kilometres as water and surfaces), heights from the Copernicus DEM GLO-30 (30 m grid, source `copdem`): its 1° GeoTIFF tiles come from AWS Open Data (no account) into git-ignored `data/dem/` (30–45 MB each, shared by all trails), read with rasterio and interpolated bilinearly; the sampled heights are cached in `data/raw/<slug>/elevation-glo30.json`. It is a surface model, so in forests it measures the treetops. Its licence requires the notice in the source record ("produced using Copernicus WorldDEM-30 …") and the liability disclaimer in the legal notice; keep both. National lidar models (Saxony DGM1, Czech DMR 5G) are candidates in docs/data-sources.md, not in use: one profile must not mix terrain models. After rerunning this step, rerun pipeline.climate (its places are the highest and lowest point). The page shows it in the Terrain section (below). Its heights come from the terrain model and are not mixed with the stated stage elevations or ascent.
- Surfaces (`pipeline/surface.py`): `pipeline/routes.py` records which OSM ways each stage uses (`routeWays` in the derived file); the surface step downloads their tags and sorts them into natural ground, gravel, paved (surface tag first; ways tagged only `unpaved` or untagged are inferred from the way type: footpaths natural, tracks and roads gravel; the inferred share is reported and shown) or unknown. Runs are placed on the same map-line kilometres as water (each stage scaled to its simplified length), so the charts line up. The page shows them as the strip under the Terrain profile and in its Surfaces figure (below); colours `--surface-*` in `Base.astro` (also on the search cards and home page), natural colours in a fixed order: natural ground earth brown, gravel sand, paved asphalt grey (issue #15). Checked with the dataviz validator in light and dark mode: separation passes for normal and colour-blind vision; the grey fails the chroma floor by design and differs by lightness (darker than earth and sand in light mode, lighter in dark mode), and every category is named in text, so keep that when changing them.
- Landscape (`pipeline/landcover.py`, issue #3): ESA WorldCover 2021 (10 m land cover, CC BY 4.0, source id `worldcover`) at the elevation profile's samples (`route_samples()` in `pipeline/elevation.py`, shared, so both have the same kilometres; rerun it after the elevation step), read remotely from its COG tiles with rasterio; each sample takes the majority class of its 30 m square so the path itself doesn't read as bare ground. The 11 classes fold into six groups (forest, grassland and shrubs, moss and lichen, bare rock and sand, water snow and ice, farmland and villages; `GROUPS`): more colours don't stay apart for every reader. The derived `landcover` has the shares, runs along the route and the highest sample in forest. The page's Landscape section (after Terrain) shows one lane per group (no lead sentence, removed by request; the sentence built from the shares, "Mostly bare rock and sand (53%), with …", is the chart's accessible name, and the derived `highestForest` is not shown) present along the route with its share and stage ticks (a faceted strip: identity is the row and its label, so the colours `--land-*` only need to differ in their fixed order; checked with the dataviz validator in both modes). The key figure "Landscape" (issue #17) names the main group by its short name (`LAND.short`: Forest, Grassland, Moss, Rock, Water, Farmland; capitalised, "Mostly Rock", "Mainly …" under 50 %) over a small bar of every group's share in the section's colours and order; its popover lists the groups with full names and shares and links to the section. It is satellite land cover, not botany: it says what the landscape looks like, not which plants grow there.
- Steepness: `gradients()` in `src/lib/trails.ts` derives it from the elevation profile at build time (no pipeline step), in walking direction and within each stage only: consecutive stages on the map line can be hundreds of metres apart, and a gradient across that jump is fake. Bars are 200 m, the steepest climb and descent the steepest 500 m, steep means ≥ 15 % (`STEEP_PERCENT`). It colours the Terrain profile (below).
- Terrain (issues #15 and #28; of three previews for #28, approach A's chart with approach C's figures was chosen): one section for elevation, steepness and the ground, in one chart without a view toggle. The elevation profile's 200 m slices are filled on a smooth diverging ramp by their gradient (`rampFill()`: the profile's tint `--terrain-tint` at 0 %, `--grade-up-steep` / `--grade-down-steep` at ±30 % (`RAMP_MAX`) and beyond, mixed in OKLab; climbs warm, descents violet), with height gridlines and the peak; a slim strip right under the baseline (`GROUND_H`, 10 units) shows the surface along the route in the `--surface-*` colours, and the stage ticks sit below the strip. One key row: the gradient ramp and the surface swatches. Above the chart, one row of key figures in pairs, like the ascent and descent tile (`.climbs`): highest and lowest point, steepest climb and descent (the Gradient popover has the stages, degrees and metres over 500 m), km steeper than 15 % (popover: up and down), and a wider Surfaces tile with each surface's share (popover: every surface with its share, km and hint; a share under 0.5 % reads "<1%"); three columns plus the wide one from 640 px, two on phones with the surfaces across both. One crosshair tooltip shows height, gradient, stage and ground at the pointer. Both views draw the tree line, the height where trees stop growing in the trail's region (issue #20), but only where the route's highest point (terrain model) is above it; that is the rule. It comes from the record's `treeLine` (`m` the upper limit, `fromM` the lower end where the source gives a range, and a `source`): a published regional figure (forest service, national forest classification, literature), never derived from our land cover or a climate model (both were tried: land cover shows where the forest ends today, the Paulsen & Körner climate model failed in oceanic climates). Drawn as a dashed line in `--land-forest` at `m` with its label in text colour ("Tree line ≈ 2,200 m"), over a faint band down to `fromM` for a range ("Tree line 1,900–2,200 m"); the (i) names the source. Today: Alpe-Adria-Trail 2,200 m (BFW growth region 1.2), Merano 1,900–2,200 m (South Tyrol), Laugavegur 550 m (Skógræktin), West Highland Way 250–650 m (recorded, not reached: the Way tops out at 549 m), Harzer Hexen-Stieg 1,100 m (Brocken, Tübingen); the Forststeig, the Path of Sacred Forests, the Westweg and the Seensteig have none in reach (notes). Its (i) names both sources and the methods; the svg's label summarises both views.
- Climate (`pipeline/climate.py`): 30 years (1995–2024) of daily ERA5 weather from the Open-Meteo historical API at the trail's lowest and highest point (coordinates from the elevation step), asked for at the point's ERA5-Land grid cell (0.1°, the data's own resolution) and its height to 10 m (`cell()`), so a cached place stays valid while a rebuilt route's highest or lowest point stays in that cell, adjusted to their elevation, averaged per month (day high, night low, wet days ≥ 1 mm, snow days ≥ 1 cm, frost nights, precipitation, the mean daily top wind and stormy days with gusts ≥ 70 km/h; the wind feeds the difficulty rating, the climate chart doesn't show it yet); daylight is computed for the 15th of each month. Source id `era5`. The page shows season ranges (day highs low down, night lows up high, wet days, daylight) and one chart in three panels over twelve month columns, each panel with its own scale: temperature range bars for both places (`--clim-low`, `--clim-high`: the highest point a deep navy, a lavender in dark mode, so it stays apart from the wet-days blue in the shared legend; issue #24, checked with the dataviz validator), wet days at the high point with snow days as their lower segment (`--wet`, `--snow`), and daylight as a filled share of 24 h (`--daylight`, a strong yellow; in light mode below 3:1 on cream, so every pill keeps its printed value); the two places are named "lowest point" and "highest point" everywhere (strip, legend, tooltip, table), without their heights; the record's season months are shaded. Hover or tap a month for all its figures; a screen-reader table carries the same numbers.
- Difficulty (issue #16, `src/lib/difficulty.ts`, rule and reasons in docs/difficulty.md): three dimensions, Terrain (path grade = the SAC grade, climbing per km, steep stretches, natural ground), Climate (heat, cold, wet days, snow, wind; rated per month, the trail's rating spans its season months, e.g. "Moderate to Hard") and Effort (the longest day), each Easy/Moderate/Demanding/Hard (`LEVELS`). Each measure has three fixed thresholds (`SCALES`, the same for every trail); a dimension takes its hardest measure, never an average, so the page names what set it. The SAC grade is a terrain measure, not its own dimension (it would repeat half of Terrain); the search filter still uses it. The key figure "Difficulty" shows one bar per dimension (its initial beneath, as tall as its level; climate's season range lighter on top) and the hardest level as a word; its popover lists each dimension with what set it and links to the section. The Difficulty section (after the map) is a strip of one card per dimension: the label is an Explain term with each measure's four bands (the trail's band marked), then the level with a four-mark meter (`src/components/Meter.astro`: shape carries the level, not colour) and every measure with its value and month or stage, the one that set the level in bold; Path grade opens the SAC scale popover. ## Ground rules

- Only official trails: a route designated or maintained by a government body or a recognised trail association. Unofficial routes (for example the Hayduke Trail) are out of scope unless docs/scope.md says otherwise. A hut circuit run by its huts counts when it has its own official website; its `managedBy` names who runs it (docs/scope.md).
- Every figure on a page must come from a source listed in the trail's record (or, for sources used across trails, in docs/data-sources.md), with its licence and retrieval date. Check a source's licence before using it: official GPX tracks are often copyrighted, and OpenStreetMap data requires ODbL attribution.
- Trail lengths, elevation gain and similar numbers differ between sources. Show which source a number comes from rather than silently picking one, and never mix them in one figure.

## Working rules

Three rules for all future development (set 2026-10-29), on top of the mission and the ground rules:

1. **Bigger design changes start as a preview with three approaches.** A bigger design change is a new section or chart, a reworked page layout or navigation, a new page type, or a redesign of an existing component (not text edits, bug fixes, small spacing tweaks, or contrast and accessibility fixes). Build three clearly different approaches first, on real data, on one local preview page under `src/pages/preview/<topic>.astro` (labelled "Approach A/B/C", each with a one-line description of its idea and trade-off; check them in both themes and at phone width), on a local branch `preview/<topic>`, and give the user the local URL. Preview pages and branches are never pushed to `main` (everything on `main` goes live). Once the user picks one, build only that into the site on `main` and delete the preview page and branch. Issue #3 (Landscape) was the model for this.
2. **Every new trail's data is double-checked before it is reported done.** Preferred: confirm each figure (length, ascent and descent, days, season, stage distances, times and heights, termini, difficulty, sleeping and camping rules, and the region's tree line where the route might reach it) against a second, independent source (e.g. the tourism board, a national park, a national trail portal, a guidebook publisher's facts). Figures may differ by at most 10 %; a larger difference is recorded in the trail's `notes` and `dataCheck` with both values and named to the user; the page keeps the official figure (docs/scope.md). Derived figures that have an official counterpart (map-line length vs. stated length, highest point vs. stated) are checked the same way. Where no second source exists: build the site and check the figures as the trail page shows them, one by one, against the original source (catches typos and wrong conversions in the record). Either way, add a note to the record ("Data check (date): …" with what was compared and what agrees) and fill its `dataCheck` field: `date`, `against` (the second sources), `pageAgainst` (sources the built page was checked against where no second source exists) and every `deviations` entry over 10 % (`figure`, `ours`, `theirs`, `source`). The check is internal quality assurance: nothing of it is shown on the page, and a source used only for the check gets `checkOnly: true`, so the page's Sources list leaves it out. Give the user the comparison as a table. When a second source publishes a figure the first lacks (e.g. stage times), use it with its own source rather than our estimate (`stages.timesSource`, named under the stage table). All three trails were checked on 2026-10-29.
3. **What explains a chart sits behind an (i).** Sources, methods and reading notes for a graph are not caption lines under it: they go into a popover behind a small (i) icon in the chart's top-right corner (at the end of the legend row where the chart has one on top, else in a slim row of its own above the drawing; `<figcaption class="chart-info">`, absolutely placed with `<Explain icon term="About this chart" title="…">`; `Explain.svelte` has the same `icon` prop), to keep the page calm. The chart itself keeps what is needed to read it at a glance: its legend or key, axis labels and its accessible name. Labels that explain a figure stay dotted Explain terms.

- Inline charts stay small (2026-10-30: the home page went from 1.2 MB to 0.4 MB of HTML, the long trail pages about 30 % down): `src/lib/svg.ts` rounds chart coordinates to a tenth of a unit (`n1`; the trail page's `xAt`, `yAt` and `laneX` return rounded values), draws a surface strip as one path per category (`stripPaths`, runs of the same category joined by `mergeRuns`; TrailSpark and the trail page's ground strip), and the trail page's elevation slices are one path per colour (`.slice.up`/`.slice.down` with `--p`, the colour mix in the CSS). New charts with many marks should do the same: one path per colour, not one element per mark. The hover scripts read their data from one `<script type="application/json" class="chart-data">` block per chart (`jsonBlock()` in the trail page, compact tuples, `<` escaped), not from HTML-escaped data attributes (the Alpe-Adria page went from 1.37 MB to 0.76 MB with this and the landscape change); the landscape lanes are one path per group (`stripPaths`) with one tooltip at the pointer (landscape, km, stage), like the terrain chart's, instead of a title per run. Astro scopes component styles with a class (`scopedStyleStrategy: "class"` in astro.config.mjs; same specificity as the default attribute, less markup), so a script must never overwrite an element's whole `class`; use `classList`. Distances on the globe are `src/lib/geo.ts` (`kmBetween` on [lon, lat], `roundDistance`), shared by the home page and the trail map.
